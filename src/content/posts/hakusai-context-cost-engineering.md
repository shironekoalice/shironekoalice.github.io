## 这篇讲什么

如果你在做一个长期在线的 LLM 应用（聊天机器人、Agent、自动化助手），每轮对话都在烧 token、每次回复都要检索记忆，那这篇是写给你的。

我会讲四件事：

1. **为什么优化方向必须是"输入"而不是"输出"**——用真实计费比例算一笔账
2. **前缀缓存的工作原理**，以及它如何决定你的提示词结构
3. **四层工具裁剪的具体做法**，含每一步的 token 收益
4. **记忆系统与向量检索的性能优化**——嵌入线程数、六阶段检索管线、重要性评分与遗忘策略

所有数字来自一个真实项目（羽汐，日均 170 万 token 的 QQ 聊天智能体）的 API `usage` 字段和运行时日志，不是估算。

---

## 第一部分：先算清楚账

### 1.1 实测一下你的输入输出比例

大多数 LLM 应用的 token 分布是这样的：

| 场景 | 模型调用次数 | 输入 token | 输出 token |
| --- | ---: | ---: | ---: |
| 寒暄（无工具） | 1 | 6,221 | 14 |
| 带工具的日常 | 4 | 11,620 | 214 |
| 看图 | 1 | 10,236 | 11 |
| 领域问句 | 1 | 12,765 | 76 |

**输入占 99%，输出占 1%。**

第一次看到这个比例我挺意外。但想想就明白了：每轮请求都要重发人格提示词、工具定义、完整历史，而输出只是一句话。

> **行动项**：在你的应用里打一份日志，把每次 API 响应的 `usage` 字段记下来（`prompt_tokens` / `completion_tokens` / 缓存字段）。没有这份数据，后面所有优化都是盲调。

### 1.2 计费比例决定优化方向

主流模型的相对单价大致是：

| 项目 | 相对价格 |
| --- | ---: |
| 输入 | 1× |
| **缓存命中输入** | **0.1×** |
| 输出 | 4× |

把两个数据乘起来：

- 输出：贵 4 倍，但只占 1% → 优化输出收益 ≈ 0.04
- 输入：便宜，但占 99% → 优化输入收益 ≈ 0.99
- **缓存命中：只要 0.1×，且能吃掉输入的大部分** → 收益空间最大

结论：**优先做缓存前缀，其次做输入裁剪，最后才考虑输出长度。**

## 第二部分：前缀缓存原理

### 2.1 缓存是按"前缀字节"命中的

这是所有设计的根基，必须理解准确：

> 缓存按请求的**前缀**匹配。前缀中任何一个字节变化，从那个位置之后**全部失效**。

验证一下（同一把密钥、同一模型，连发三次）：

| 请求形态 | prompt | 命中 | 命中率 |
| --- | ---: | ---: | ---: |
| 完全相同的请求两次 | 1,522 | 1,520 | 99.8% |
| 同前缀、末尾不同 | 1,526 | 1,514 | 99.2% |
| 带工具定义 | 1,756 | 1,754 | 99.9% |

**关键发现：末尾变化不影响前缀命中。** 第二行和第三行证明了这点——只在尾部追加内容，前面全部还能命中。

### 2.2 由此推导出请求结构

既然缓存按前缀命中，那就要把**变化最少的内容放最前面**：

```text
[静态人格提示词]   ← 全进程只构建一次，字节恒定
[工具定义数组]     ← 必须在历史之前，且要稳定
[历史对话]         ← 严格递增，上一轮发过的就是本轮前缀
[本轮动态状态]     ← 每轮变化，放最后
[本轮消息]
```

### 2.3 两个必须遵守的配套细节

**细节一：任何每轮都会变的东西，绝不能放静态段。**

我原来把"发送者信息"（QQ 号、昵称）放在静态提示词里，看起来合理——毕竟它是"人格设定的一部分"。但同一个用户在群聊和私聊之间切换时，这个值会变，于是整段前缀（人格 + 全部历史）瞬间失效。

现在的做法：发送者信息一律放动态段。

**细节二：静态段里的内容要"冻结"。**

表情标签列表我放在静态段里一次性固化。代价是运行期新增的表情类别不会更新。这是为了字节稳定接受的取舍——**静态段里放什么东西，等价于宣布"这些东西的字节永远不会变"**。

### 2.4 真实命中轨迹长什么样

多轮对话实测：

```text
轮次「在吗」              prompt= 4,318  cached=   186  (  4%)  ← 冷启动
轮次「今天大盘怎么样」     prompt= 7,936  cached= 4,162  ( 52%)
                         prompt= 8,269  cached= 7,936  ( 95%)
轮次「视频平台有什么新内容」 prompt=11,489  cached= 4,169  ( 36%)  ← 见下
                         prompt=13,128  cached=11,489  ( 87%)
```

第三组那个 36% 是问题所在：**工具集变了，排在历史之前的工具数组一变，后面全部失效。**

这就是第三部分要解决的问题。

## 第三部分：四层工具裁剪（可照做）

### 3.1 问题：工具定义是最肥的一块

拆开一次请求的输入：

| 部分 | token |
| --- | ---: |
| 工具定义 JSON schema | 13,400（全量时） |
| 动态上下文 | 2,100 |
| 静态人格提示词 | 1,400 |

工具定义占了绝大部分。81 个工具的 schema 全量塞进去就是 13.4K。

### 3.2 第一层：按类别加载

**做法**：给每个工具打类别标签，用关键词映射到类别。命中哪类只加哪类，没命中只带基础集。

```python
# 简化示意
CATEGORY_KEYWORDS = {
    "stock": ["股票", "大盘", "K线", "持仓"],
    "video": ["视频", "UP主", "番剧"],
    "search": ["搜", "查一下", "最新"],
}

def select_tools(message: str) -> list[Tool]:
    categories = {c for c, kws in CATEGORY_KEYWORDS.items()
                  if any(kw in message for kw in kws)}
    tools = list(BASE_TOOLS)          # 基础集常驻
    for c in categories:
        tools.extend(CATEGORY_TOOLS[c])
    return tools
```

**收益**：改造前是"命中就加载全部 81 个工具"，实测 **85% 的轮次在背全量却只用 10 个**。

**副作用（重要）**：这一层会破坏缓存。见 3.5。

### 3.3 第二层：基础集瘦身

把低频工具从常驻集里挪出去，改成按需加载：

| 版本 | 工具数 | token |
| --- | ---: | ---: |
| 原基础集 | 23 | 3,340 |
| 现基础集 | 17 | 2,244 |

省下 1,945 token。判断标准很简单：**过去一周有没有被主动调用过**。没有就挪出去。

### 3.4 第三层：类别白名单

这一层的思路和上面不同：很多能力是**通过命令直接调 API** 的，根本不需要经过模型的工具数组。既然模型不需要"看见"这些工具，就从可见列表里裁掉：

| 类别 | 裁剪前 | 裁剪后 |
| --- | ---: | ---: |
| 股票 | 18 | 16 |
| 视频平台 | 23 | 13 |
| 社交平台 | 7 | 6 |

**判断标准**：这个工具的调用是否总是由应用代码触发、而不是由模型决策触发？如果是，它就不该出现在 schema 里。

### 3.5 第四层：工具集"粘住"（解决缓存失效）

前三层都在省 token，但都在破坏缓存——因为工具数组排在历史之前，一变就把前缀全废了。

**做法**：某个类别一旦加载过，本会话后续就一直带着它。

```python
class SessionState:
    stuck_categories: set[str] = set()

    def select_tools(self, message):
        new_cats = match_categories(message) - self.stuck_categories
        if new_cats:
            self.stuck_categories |= new_cats   # 永久带上
        return build_tools(self.stuck_categories)
```

**效果**：缓存失效从"每次关键词命中都发生"变成"每个会话最多发生一次"。

**这是一个典型的取舍问题**：分类加载省 token，但破缓存；粘住保缓存，但会多带一些工具。答案不是二选一，而是"让失效只发生一次，然后保持稳定"。

### 3.6 优化结果

同一条消息、同一干净会话的 A/B 对照：

| 消息 | 优化前 | 优化后 | 降幅 |
| --- | ---: | ---: | ---: |
| 「在吗」 | 5,710 | 4,566 | −20% |
| 「今天大盘怎么样」 | 16,428 | 7,280 | **−56%** |
| 「视频平台最近有什么新内容」 | 16,431 | 6,601 | **−60%** |

工具定义单项：13,456 → 2,244（基础）/ 3,958（视频平台）/ 4,950（股票）。

按日均 170 万 token 算，每天省 60~80 万。

## 第四部分：三个反直觉的坑

### 4.1 别用"工具名清单"代替 schema

我试过这个方案：请求里只放工具名列表，模型需要时再取完整 schema。理论上能把 13.4K 压到几百 token。

实测：

| 请求形态 | 模型是否发起工具调用 |
| --- | --- |
| 精简工具 + 工具名目录文本 | **否**（改在正文里写 `工具名 {}`） |
| 精简工具，无目录 | 是 |
| 全量工具，无目录 | 是 |

**只要模型看到工具名清单，它就放弃结构化调用、改用文本模仿。** 这个方案对测试过的所有主模型都不成立。

教训：**省 token 不能以破坏协议为代价。** 模型的工具调用行为对提示形态极其敏感，任何"聪明"的压缩方案都必须实测。

### 4.2 上下文太长会把图片挤没

一个视觉模型在动态上下文 **1,500 字符**时还能正常看图，**3,002 字符就完全看不见图片**。

而且它不报错——模型会正常回复"无法识别图片"，让你以为是图片格式问题。

**做法**：带图轮次把动态上下文压到 1,200 字符以内，且只保留决定语气的那几段（时间/心情/状态），丢掉技能清单和工具偏好。

### 4.3 精简通道可能比全量更贵

我做过一条"轻量通道"：短消息走精简路径，跳过动态上下文和工具定义。直觉上一定更便宜。

**但它现在是关闭的。** 因为主模型支持缓存之后，**全量上下文走缓存可能比精简上下文走非缓存还便宜**：

| 方案 | token | 单价 | 实际成本 |
| --- | ---: | ---: | ---: |
| 全量 + 缓存命中 | 8,000 | 0.1× | 800 |
| 精简 + 无缓存 | 2,000 | 1× | 2,000 |

（示意数字，实际要用真实账单验证）

**教训**：这类决策必须用真实计费验证。凭"token 数变少了"就认为更便宜，会做反。

## 第五部分：工程细节清单

这些和成本不直接相关，但都影响"能不能稳定跑起来"。

### 5.1 别静默吞掉工具调用

模型偶尔吐出非法 JSON 参数，比如 `"ratio":3:4`（缺引号）。如果 `json.loads` 失败就丢弃调用，现象是"有时候能用、有时候毫无反应"，随机且极难排查——因为模型以为自己调过了。

**7 级降级**：

| 级别 | 处理 |
| --- | --- |
| 1 | 标准 JSON 解析 |
| 2 | 移除代码块包装、截取最外层花括号 |
| 3 | 修复尾逗号 |
| 4 | 给未加引号的值补引号 |
| 5 | 单引号转双引号 |
| 6 | 清理控制字符、转义裸换行 |
| 7 | **仍失败则带空参数执行**，让工具自己报告缺参 |

核心原则：**宁可执行失败让用户看到错误，也不静默吞掉调用。**

### 5.2 判据要选对层级

一个真实 bug：用户发表情包，机器人回"你想问什么呀"。

根因是判断"消息是否为空"时用的是"成功下载的图片字节列表"——而表情包多是 GIF 或外链，下载经常失败，列表为空就被判成"什么都没说"。

**正确的判据是"消息里有没有图片段"，而不是"我们有没有成功处理它"。**

这类缺陷的症状会骗人。排查时先问：我判断的这件事，和用户实际做的事是同一件事吗？

### 5.3 多个正则串联时，顺序就是逻辑

有个输出是 `&喵&amp;`（一半转义一半没有）。旧代码把中间标签吃掉后，反而留下纯文本 `amp;`。

根因：先跑了单 `&` 的正则，正好用掉了 `&amp;` 里的那个 `&`。

修复只是把两行顺序调换。**先统一还原转义，再做标记剥离。**

### 5.4 同一个动作有多个出口时，把契约测试化

系统里"说一句话"有 6 个出口。清洗、记录、写历史这套动作要在每个出口都做一遍，漏一个就是线上 bug。

一天之内实测漏了 4 个出口。

**对策不是"下次注意"，而是测试化**：维护一张出口登记表，新增出口必须同时改文档和测试，否则 CI 变红。

宁可让 CI 失败，也不要让协议标记漏到用户面前。

## 第六部分：记忆系统与向量库的性能优化

上下文裁剪解决的是"每轮发多少"，记忆系统解决的是"每轮该想起什么"。后者如果没有约束，会变成第二个成本黑洞——检索慢了拖响应，召回多了塞上下文。

### 6.1 先给规模定个上限

分层设计时，容量上限应该写死，而不是"能存多少存多少"：

| 层 | 存储 | 容量 | 作用 |
| --- | --- | ---: | --- |
| 短期 | 内存 + JSON | 50 条 | 当前会话上下文 |
| 长期 | 向量库 | 500 条 | 跨会话知识 |
| 日记 | 长期库内标记 | — | 叙事性回忆 |
| 语义事实 | 长期库内标记 | — | 睡眠巩固时提取 |
| 群共享 | 独立向量库 | — | 群体共同经历 |

小库的好处是全在内存里，检索没有 IO。我的长期库 500 条，向量数据 66MB、状态数据 41MB——这个量级用文件 + numpy 就够了，不需要上专门的向量数据库服务。

> **判断标准**：条目数在万级以下，用文件 + 暴力检索完全够用；十万级以上再考虑 HNSW 之类的近似索引。过早引入向量库服务，运维成本远大于收益。

### 6.2 嵌入模型的线程数：越多越慢

这条很反直觉，但实测如此。本地 512 维中文嵌入模型，4 核环境：

| 线程数 | 单条延迟 |
| ---: | ---: |
| 4 | 207ms |
| 2 | 30ms |
| 1 | **20ms** |

**线程越多反而越慢**——小模型的矩阵运算量不足以摊平分发开销，线程同步成本反而成了主导。

> **行动项**：把 `OMP_NUM_THREADS` / `torch.set_num_threads` 设为 1~2 实测对比。默认值往往是"CPU 核数"，对嵌入模型来说是错的。

### 6.3 六阶段检索管线

朴素做法是"向量召回 top-k 直接塞进提示词"。实测效果一般，因为向量相似度会被高频短语带跑偏。现在是六个阶段：

```text
① 向量召回    取 top(max(k×10, 50))，记录排名与距离
② 来源闸门    只允许"跟用户聊过天"的记忆；群经历额外做淡出判定
③ BM25 精排   中文必须分词，k1=1.5, b=0.75
④ RRF 融合    两路各贡献 1/(60 + 排名)，k=60
⑤ 加权打分    语义 0.55 + 关键词 0.12 + 关键信息 0.08
              + 重要性 0.10 + 时间衰减 0.08 + 标签 0.07
⑥ 去重再巩固  按内容前 100 字去重；被检索到则提升重要性
```

几个值得单独说的点：

**③ 中文 BM25 必须分词。** 不分词时分数恒为 0——不是效果差，是根本算不出来。这是一个很容易忽略的沉默失败。

**④ 用 RRF 而不是加权平均融合两路。** RRF（Reciprocal Rank Fusion）只看排名不看分数，天然免疫两路分数量纲不一致的问题。k=60 是原论文的常用值。

**① 召回数是自适应的**，不是固定 top-k：

| 库规模 | 召回条数 |
| --- | ---: |
| ≤20 条 | 2 |
| ≤100 条 | 4 |
| 更大 | 6 |

库小的时候多召回全是噪声，反而降低质量。

**⑤ 时间衰减的权重刻意压得很低**：`0.5 ^ (小时数 / 72)`，半衰期 72 小时，但权重只有 0.08。

为什么？因为它的作用是**同分时的平手裁决**，不该压过语义相似度。如果把时间衰减权重调高，会变成"总是想起最近的"，长期记忆就白存了。

> 这条也是我在看自己数据时发现的：时间衰减"只在同分时起作用"，反过来说明加权打分对语义的区分度可能不足。所以列进了未来的改进项——加一层交叉编码器精排。

### 6.4 重要性评分决定写不写

不是所有对话都值得进长期记忆。用六维评分过滤，基础分 0.3，向上叠加：

| 维度 | 规则 | 上限贡献 |
| --- | --- | ---: |
| 意外度 | 与已存记忆的最近邻距离归一化 | 0.25 |
| 情绪强度 | 分档递增 | 0.15 |
| 信息密度 | 关键信息段数 × 0.04 | 0.20 |
| 语义重要性 | 身份类 0.15 / 计划类 0.10 / 喜好类 0.05 | 0.15 |
| 自我提及 | +0.10 | 0.10 |
| 对话长度 | 超 300 字 +0.10 | 0.10 |

**"意外度"这个维度值得单独讲**：用它与已有记忆的向量最近邻距离衡量"这句话有多不像我已经知道的东西"。越不像 → 信息量越大 → 越值得记。

这是"预测误差驱动记忆编码"的工程化粗糙类比——不需要真的算预测误差，用向量距离当代理指标就够了。

两个落库闸门：

- 重要性 < 0.3 **且** 情绪强度 < 0.7 → 不写长期库
- 与已有记忆相似度 ≥ 0.8 → **合并更新**而不是新增

第二条尤其重要：不做合并，同一件事会被反复记录，长期库很快被同类内容填满。

### 6.5 遗忘与巩固：定期清理比写入更重要

**每 6 小时滚动执行一次**（带 ±0.5 小时抖动，避免固定时刻抖动）：

```text
① 短期 → 长期     重要性 ≥ 0.35 的未归档记忆
                  若 ≥3 条，先让模型提取语义事实（每条 10-30 字）
② 近重复合并      相似度 > 0.9 的组，保留最重要的一条
③ 陈旧衰减        >7 天且重要性 <0.5 → 降 30%
                  >30 天且重要性 <0.3 → 降到 0.05，等冷存储清理
```

为什么是滚动而不是"固定在夜间"？因为这是长期在线服务，没有"夜间空闲期"这个概念——随机化的滚动任务反而更均匀。

**② 那一步是防止库膨胀的关键。** 500 条上限下，如果只写不合并，两周就满了；合并之后，实际增长速率取决于"新信息的多样性"，而不是对话量。

### 6.6 压缩：三层触发

| 触发条件 | 动作 |
| --- | --- |
| 超 30 天 | 重要性按 `max(0.3, 1 - 月数×0.05)` 衰减 |
| 同主题 ≥5 条 | 交给模型压成 100-150 字摘要，标记为"核心"（不参与淘汰） |
| 超容量上限 | 按重要性升序淘汰，写入冷存储目录 |

"核心记忆不参与淘汰"这一条很关键：主题摘要压缩后信息密度高，如果被淘汰掉，等于把一组相关记忆全丢了。

### 6.7 一个和记忆无关但同类的性能坑

**高频写盘会堵住事件循环。**

群聊消息每条都全量落盘（写 JSON 状态），在事件循环里造成 **50-90 毫秒**级阻塞，会话越多越糟。

修复方式：脏标记 + 后台线程每 2 秒合并写一次。

```python
# 简化示意
dirty = False

def on_message(msg):
    global dirty
    inbox.append(msg)
    dirty = True          # 只置标记，不落盘

def flush_loop():         # 后台线程
    while running:
        time.sleep(2)
        if dirty:
            atomic_write(state)   # 同目录临时文件 → fsync → 原子替换
            dirty = False
```

**原子写是配套必须的**：临时文件 → 写 → `fsync` → 原子替换，避免进程被杀时留下半个 JSON。

> 这类问题在本地开发时完全看不出来（因为消息量小），上线后才会暴露。凡是"每条消息都做一次 IO"的地方，都该考虑合批。

## 最后：一份可以照着做的检查清单

1. **先打日志**：记录每次调用的 `prompt_tokens` / `completion_tokens` / 缓存字段。没有数据不要优化
2. **量一下输入输出比例**：确认输入是不是占 95% 以上
3. **重排请求结构**：静态 → 工具 → 历史 → 动态 → 当前消息
4. **冻结静态段**：把每轮会变的东西全部挪到动态段
5. **工具分类加载**：先做关键词映射，别急着上模型路由
6. **工具集粘住**：让缓存失效每会话只发生一次
7. **验证缓存命中率**：构造"同前缀不同尾部"的请求，看命中率是否 >99%
8. **A/B 对照**：同一条消息、同一个干净会话，只改一个变量，取 `usage` 字段对比
9. **嵌入线程数调到 1~2**：小模型多线程反而更慢，默认值通常是错的
10. **中文 BM25 记得分词**：不分词时分数恒为 0，是沉默失败
11. **写入前先查重合并**：相似度 ≥0.8 合并更新，否则库会被同类内容填满
12. **定期遗忘**：只写不删，500 条上限两周就满
13. **高频写盘合成批**：脏标记 + 后台线程合并写，配原子替换
14. **别信直觉**：任何"这个肯定更省"的改动都要用账单和实测验证
