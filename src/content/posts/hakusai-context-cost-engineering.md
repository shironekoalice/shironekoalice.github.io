## 这篇讲什么

如果你在做一个长期在线的 LLM 应用（聊天机器人、Agent、自动化助手），每轮对话都在烧 token，那这篇是写给你的。

我会讲三件事：

1. **为什么优化方向必须是"输入"而不是"输出"**——用真实计费比例算一笔账
2. **前缀缓存的工作原理**，以及它如何决定你的提示词结构
3. **四层工具裁剪的具体做法**，含每一步的 token 收益

所有数字来自一个真实项目（羽汐，日均 170 万 token 的 QQ 聊天智能体）的 API `usage` 字段，不是估算。

---

## 第一部分：先算清楚账

### 1.1 实测一下你的输入输出比例

大多数 LLM 应用的 token 分布是这样的：

| 场景 | 模型调用次数 | 输入 token | 输出 token |
| --- | ---: | ---: | ---: |
| 寒暄（无工具） | 1 | 6,221 | 14 |
| 带工具的日常 | 4 | 11,620 | 214 |
| 看图 | 1 | 10,236 | 11 |
| 领域问句 | 1 | 12,765 | 76 |

**输入占 99%，输出占 1%。**

第一次看到这个比例我挺意外。但想想就明白了：每轮请求都要重发人格提示词、工具定义、完整历史，而输出只是一句话。

> **行动项**：在你的应用里打一份日志，把每次 API 响应的 `usage` 字段记下来（`prompt_tokens` / `completion_tokens` / 缓存字段）。没有这份数据，后面所有优化都是盲调。

### 1.2 计费比例决定优化方向

主流模型的相对单价大致是：

| 项目 | 相对价格 |
| --- | ---: |
| 输入 | 1× |
| **缓存命中输入** | **0.1×** |
| 输出 | 4× |

把两个数据乘起来：

- 输出：贵 4 倍，但只占 1% → 优化输出收益 ≈ 0.04
- 输入：便宜，但占 99% → 优化输入收益 ≈ 0.99
- **缓存命中：只要 0.1×，且能吃掉输入的大部分** → 收益空间最大

结论：**优先做缓存前缀，其次做输入裁剪，最后才考虑输出长度。**

## 第二部分：前缀缓存原理

### 2.1 缓存是按"前缀字节"命中的

这是所有设计的根基，必须理解准确：

> 缓存按请求的**前缀**匹配。前缀中任何一个字节变化，从那个位置之后**全部失效**。

验证一下（同一把密钥、同一模型，连发三次）：

| 请求形态 | prompt | 命中 | 命中率 |
| --- | ---: | ---: | ---: |
| 完全相同的请求两次 | 1,522 | 1,520 | 99.8% |
| 同前缀、末尾不同 | 1,526 | 1,514 | 99.2% |
| 带工具定义 | 1,756 | 1,754 | 99.9% |

**关键发现：末尾变化不影响前缀命中。** 第二行和第三行证明了这点——只在尾部追加内容，前面全部还能命中。

### 2.2 由此推导出请求结构

既然缓存按前缀命中，那就要把**变化最少的内容放最前面**：

```text
[静态人格提示词]   ← 全进程只构建一次，字节恒定
[工具定义数组]     ← 必须在历史之前，且要稳定
[历史对话]         ← 严格递增，上一轮发过的就是本轮前缀
[本轮动态状态]     ← 每轮变化，放最后
[本轮消息]
```

### 2.3 两个必须遵守的配套细节

**细节一：任何每轮都会变的东西，绝不能放静态段。**

我原来把"发送者信息"（QQ 号、昵称）放在静态提示词里，看起来合理——毕竟它是"人格设定的一部分"。但同一个用户在群聊和私聊之间切换时，这个值会变，于是整段前缀（人格 + 全部历史）瞬间失效。

现在的做法：发送者信息一律放动态段。

**细节二：静态段里的内容要"冻结"。**

表情标签列表我放在静态段里一次性固化。代价是运行期新增的表情类别不会更新。这是为了字节稳定接受的取舍——**静态段里放什么东西，等价于宣布"这些东西的字节永远不会变"**。

### 2.4 真实命中轨迹长什么样

多轮对话实测：

```text
轮次「在吗」              prompt= 4,318  cached=   186  (  4%)  ← 冷启动
轮次「今天大盘怎么样」     prompt= 7,936  cached= 4,162  ( 52%)
                         prompt= 8,269  cached= 7,936  ( 95%)
轮次「视频平台有什么新内容」 prompt=11,489  cached= 4,169  ( 36%)  ← 见下
                         prompt=13,128  cached=11,489  ( 87%)
```

第三组那个 36% 是问题所在：**工具集变了，排在历史之前的工具数组一变，后面全部失效。**

这就是第三部分要解决的问题。

## 第三部分：四层工具裁剪（可照做）

### 3.1 问题：工具定义是最肥的一块

拆开一次请求的输入：

| 部分 | token |
| --- | ---: |
| 工具定义 JSON schema | 13,400（全量时） |
| 动态上下文 | 2,100 |
| 静态人格提示词 | 1,400 |

工具定义占了绝大部分。81 个工具的 schema 全量塞进去就是 13.4K。

### 3.2 第一层：按类别加载

**做法**：给每个工具打类别标签，用关键词映射到类别。命中哪类只加哪类，没命中只带基础集。

```python
# 简化示意
CATEGORY_KEYWORDS = {
    "stock": ["股票", "大盘", "K线", "持仓"],
    "video": ["视频", "UP主", "番剧"],
    "search": ["搜", "查一下", "最新"],
}

def select_tools(message: str) -> list[Tool]:
    categories = {c for c, kws in CATEGORY_KEYWORDS.items()
                  if any(kw in message for kw in kws)}
    tools = list(BASE_TOOLS)          # 基础集常驻
    for c in categories:
        tools.extend(CATEGORY_TOOLS[c])
    return tools
```

**收益**：改造前是"命中就加载全部 81 个工具"，实测 **85% 的轮次在背全量却只用 10 个**。

**副作用（重要）**：这一层会破坏缓存。见 3.5。

### 3.3 第二层：基础集瘦身

把低频工具从常驻集里挪出去，改成按需加载：

| 版本 | 工具数 | token |
| --- | ---: | ---: |
| 原基础集 | 23 | 3,340 |
| 现基础集 | 17 | 2,244 |

省下 1,945 token。判断标准很简单：**过去一周有没有被主动调用过**。没有就挪出去。

### 3.4 第三层：类别白名单

这一层的思路和上面不同：很多能力是**通过命令直接调 API** 的，根本不需要经过模型的工具数组。既然模型不需要"看见"这些工具，就从可见列表里裁掉：

| 类别 | 裁剪前 | 裁剪后 |
| --- | ---: | ---: |
| 股票 | 18 | 16 |
| 视频平台 | 23 | 13 |
| 社交平台 | 7 | 6 |

**判断标准**：这个工具的调用是否总是由应用代码触发、而不是由模型决策触发？如果是，它就不该出现在 schema 里。

### 3.5 第四层：工具集"粘住"（解决缓存失效）

前三层都在省 token，但都在破坏缓存——因为工具数组排在历史之前，一变就把前缀全废了。

**做法**：某个类别一旦加载过，本会话后续就一直带着它。

```python
class SessionState:
    stuck_categories: set[str] = set()

    def select_tools(self, message):
        new_cats = match_categories(message) - self.stuck_categories
        if new_cats:
            self.stuck_categories |= new_cats   # 永久带上
        return build_tools(self.stuck_categories)
```

**效果**：缓存失效从"每次关键词命中都发生"变成"每个会话最多发生一次"。

**这是一个典型的取舍问题**：分类加载省 token，但破缓存；粘住保缓存，但会多带一些工具。答案不是二选一，而是"让失效只发生一次，然后保持稳定"。

### 3.6 优化结果

同一条消息、同一干净会话的 A/B 对照：

| 消息 | 优化前 | 优化后 | 降幅 |
| --- | ---: | ---: | ---: |
| 「在吗」 | 5,710 | 4,566 | −20% |
| 「今天大盘怎么样」 | 16,428 | 7,280 | **−56%** |
| 「视频平台最近有什么新内容」 | 16,431 | 6,601 | **−60%** |

工具定义单项：13,456 → 2,244（基础）/ 3,958（视频平台）/ 4,950（股票）。

按日均 170 万 token 算，每天省 60~80 万。

## 第四部分：三个反直觉的坑

### 4.1 别用"工具名清单"代替 schema

我试过这个方案：请求里只放工具名列表，模型需要时再取完整 schema。理论上能把 13.4K 压到几百 token。

实测：

| 请求形态 | 模型是否发起工具调用 |
| --- | --- |
| 精简工具 + 工具名目录文本 | **否**（改在正文里写 `工具名 {}`） |
| 精简工具，无目录 | 是 |
| 全量工具，无目录 | 是 |

**只要模型看到工具名清单，它就放弃结构化调用、改用文本模仿。** 这个方案对测试过的所有主模型都不成立。

教训：**省 token 不能以破坏协议为代价。** 模型的工具调用行为对提示形态极其敏感，任何"聪明"的压缩方案都必须实测。

### 4.2 上下文太长会把图片挤没

一个视觉模型在动态上下文 **1,500 字符**时还能正常看图，**3,002 字符就完全看不见图片**。

而且它不报错——模型会正常回复"无法识别图片"，让你以为是图片格式问题。

**做法**：带图轮次把动态上下文压到 1,200 字符以内，且只保留决定语气的那几段（时间/心情/状态），丢掉技能清单和工具偏好。

### 4.3 精简通道可能比全量更贵

我做过一条"轻量通道"：短消息走精简路径，跳过动态上下文和工具定义。直觉上一定更便宜。

**但它现在是关闭的。** 因为主模型支持缓存之后，**全量上下文走缓存可能比精简上下文走非缓存还便宜**：

| 方案 | token | 单价 | 实际成本 |
| --- | ---: | ---: | ---: |
| 全量 + 缓存命中 | 8,000 | 0.1× | 800 |
| 精简 + 无缓存 | 2,000 | 1× | 2,000 |

（示意数字，实际要用真实账单验证）

**教训**：这类决策必须用真实计费验证。凭"token 数变少了"就认为更便宜，会做反。

## 第五部分：工程细节清单

这些和成本不直接相关，但都影响"能不能稳定跑起来"。

### 5.1 别静默吞掉工具调用

模型偶尔吐出非法 JSON 参数，比如 `"ratio":3:4`（缺引号）。如果 `json.loads` 失败就丢弃调用，现象是"有时候能用、有时候毫无反应"，随机且极难排查——因为模型以为自己调过了。

**7 级降级**：

| 级别 | 处理 |
| --- | --- |
| 1 | 标准 JSON 解析 |
| 2 | 移除代码块包装、截取最外层花括号 |
| 3 | 修复尾逗号 |
| 4 | 给未加引号的值补引号 |
| 5 | 单引号转双引号 |
| 6 | 清理控制字符、转义裸换行 |
| 7 | **仍失败则带空参数执行**，让工具自己报告缺参 |

核心原则：**宁可执行失败让用户看到错误，也不静默吞掉调用。**

### 5.2 判据要选对层级

一个真实 bug：用户发表情包，机器人回"你想问什么呀"。

根因是判断"消息是否为空"时用的是"成功下载的图片字节列表"——而表情包多是 GIF 或外链，下载经常失败，列表为空就被判成"什么都没说"。

**正确的判据是"消息里有没有图片段"，而不是"我们有没有成功处理它"。**

这类缺陷的症状会骗人。排查时先问：我判断的这件事，和用户实际做的事是同一件事吗？

### 5.3 多个正则串联时，顺序就是逻辑

有个输出是 `&喵&amp;`（一半转义一半没有）。旧代码把中间标签吃掉后，反而留下纯文本 `amp;`。

根因：先跑了单 `&` 的正则，正好用掉了 `&amp;` 里的那个 `&`。

修复只是把两行顺序调换。**先统一还原转义，再做标记剥离。**

### 5.4 同一个动作有多个出口时，把契约测试化

系统里"说一句话"有 6 个出口。清洗、记录、写历史这套动作要在每个出口都做一遍，漏一个就是线上 bug。

一天之内实测漏了 4 个出口。

**对策不是"下次注意"，而是测试化**：维护一张出口登记表，新增出口必须同时改文档和测试，否则 CI 变红。

宁可让 CI 失败，也不要让协议标记漏到用户面前。

## 最后：一份可以照着做的检查清单

1. **先打日志**：记录每次调用的 `prompt_tokens` / `completion_tokens` / 缓存字段。没有数据不要优化
2. **量一下输入输出比例**：确认输入是不是占 95% 以上
3. **重排请求结构**：静态 → 工具 → 历史 → 动态 → 当前消息
4. **冻结静态段**：把每轮会变的东西全部挪到动态段
5. **工具分类加载**：先做关键词映射，别急着上模型路由
6. **工具集粘住**：让缓存失效每会话只发生一次
7. **验证缓存命中率**：构造"同前缀不同尾部"的请求，看命中率是否 >99%
8. **A/B 对照**：同一条消息、同一个干净会话，只改一个变量，取 `usage` 字段对比
9. **别信直觉**：任何"这个肯定更省"的改动都要用账单验证
